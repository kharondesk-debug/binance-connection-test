# Binance Funding Alert Bot v4.1 — 일일 오류 보고

## 이번 변경 범위
운영 v4의 원본 19개 파일을 별도 폴더로 복사한 뒤 진단 알림만 변경했습니다. 원본 ZIP·소스와 GitHub main의 19개 blob 해시를 대조했습니다. A/B 및 신규 상장 승인 요청의 메시지·판정·즉시 발송, 승인 정책, WebSocket, 180초 REST·복구 동작은 유지합니다.

- 진단은 기존 15초 검사와 실제 서비스 실패·성공 관측으로 수집하고 `/status`에 계속 표시합니다. `DIAGNOSTIC` 개별 텔레그램 발송은 없습니다.
- KST 00:00에 직전 날짜를 고정 ID `daily:YYYY-MM-DD`로 한 번 등록합니다. 전용 1초 스케줄러이므로 잠금·네트워크·전송 대기 상황에 따라 실제 발송은 늦어질 수 있습니다. 지연 보고도 원래 집계 날짜와 생성 시각을 유지합니다.
- 같은 원인의 지속 장애는 1사건, 성공으로 복구를 확인한 뒤 재발하면 새 사건입니다. 337개 동시 가격 이력 부족은 1사건/최대 동시 영향337개로 표시합니다. 자정을 넘는 장애는 신규 사건과 전일 지속을 구분합니다.
- 발생이 없다고 확인한 날에는 `오늘 발생한 오류 없음`을 보냅니다. 최초 가동 전 시간·재시작·DB 단절·관측하지 못한 날짜는 `확인 불가`를 표시합니다. 오류 종류/사건 수와 영향 종목 수는 서로 다른 수치입니다.
- 새 `bot_daily_days`, `bot_daily_reports`, `bot_daily_legacy`와 작은 `bot_meta` 체크포인트를 멱등 생성합니다. 일일 보고서는 기존 `bot_pending` 용량을 사용하지 않으며 발송 시 A/B·승인 요청을 먼저 선택합니다.
- 남아 있는 `diag:` 대기 행만 같은 트랜잭션에서 원문 보관 후 전환합니다. 메시지 수를 장애 사건 수로 추정하지 않습니다. A/B·승인 큐와 가격 이력은 삭제·변경하지 않습니다.
- 일일 원장과 완료 날짜는 DB에 보존합니다. 현재 날짜·활성 원인만 메모리에 유지하고 DB 단절 중 닫힌 날짜 캐시는 최대2개입니다. 정상 반복 장애의 마지막 관측은 메모리에서 갱신하고 작은 DB 체크포인트를 분당1회 기록합니다. 상태 전이는 바로 저장합니다.
- 메시지는 최대3,800 UTF-16 단위로 줄입니다. 정상 범위에서는 표기·범례 압축으로 각 원인별 필수 수치를 유지하며, 극단적인 상세량은 전체 JSON의 무손실 압축과 DB 원장을 사용합니다. 원인 분류 한도128개 초과나 DB 장애 중 유실 가능성은 정확성 한계를 표시합니다.
- Telegram 성공 응답/DB 확인이 끊긴 모호한 경우에는 재시도로 중복 배달될 가능성이 남습니다. 등록 중복 방지와 외부 배달의 정확히1회 보장은 다릅니다.

## 오프라인 결과와 메모리 영향
총251개 통과/0개 실패: 기존185개 회귀 항목과 신규66개입니다. 기존 항목 중 즉시 진단을 요구하던4개만 일일 정책에 맞게 기대값을 수정하고 모의 저장소 인터페이스를 확장했습니다. 실제 Binance·Telegram·운영 DB를 사용하지 않았습니다.
77개 서로 다른 장애 원인·시각, 현재 원장·닫힌 날짜·스냅샷을 포함한 모의 보고서는 2,809 UTF-16 단위였고 Python 추적 할당 최대는 약233KiB였습니다. 이는 추가 집계 부분의 할당 측정이며 서버 RSS·256MB 실서버 장기 운용 보장이 아닙니다. 기존 승인 종목 이력 선택 로딩 구조는 바꾸지 않았습니다.

## 수동 반영 및 안전한 배포
이번 작업은 로컬 제작만 수행하며 GitHub push, Northflank 배포·재시작, 운영 PostgreSQL 변경·Telegram 발송을 하지 않습니다.

사용자 별도 승인 후 반영할 운영 파일: `app.py`, `storage.py`, `daily_report.py`, `Dockerfile`, `.dockerignore`.
문서/검증 파일: `README.md`, `test_incidents.py`, `test_v4_runtime.py`, `test_daily_report.py`, `test_daily_storage.py`, `test_daily_runtime.py`.
나머지12개 원본 파일은 그대로 유지합니다. 삭제할 원본 파일은 없습니다.

1. 변경 차이를 검토하고 위 unittest 전체 검증을 다시 실행합니다. 비밀값은 기존 Secret Group에만 유지합니다.
2. 기존 인스턴스를 정상 중지하고 같은 서비스·DB·무료 사양에 단일 인스턴스로 교체합니다. 복제 봇을 동시에 실행하지 않습니다.
3. 첫 DB 연결이 기존 데이터를 보존하며 테이블·체크포인트를 추가하고 남은 진단 행만 보관 전환합니다. DB 초기화·DROP·가격 이력 삭제를 하지 않습니다.
4. `/status`·`/watch`로 승인 정책/데이터 신선도와 기존 명령을 확인합니다. 가짜 A/B·신규 상장 메시지로 시험하지 않습니다.
5. 다음 KST 자정 보고서의 날짜·고정 ID·별도 큐·완료 표식을 확인합니다. 장애 시 원래 날짜 보고서가 재시도되는지 확인합니다.
6. 되돌릴 때는 먼저 단일 인스턴스를 중지하고 보존한 원본 v4 소스로 교체합니다. 추가 테이블은 삭제하지 않습니다. 이전 v4로 돌아가면 즉시 진단 정책도 돌아옵니다.

- approval_policy.json은 사용자가 확정한 2026-10-15 스냅샷입니다. 전체 고유 계약 525 = APPROVED 337 + BLOCKED 187 + REVIEW 1(1000RATSUSDT).
- 고정 SHA와 심볼 집합을 검증하고 최초 DB 연결에서 한 번만 bot_watch 및 approval_seed_v4 메타를 초기화합니다. 이후 텔레그램 변경을 초기 명단으로 덮어쓰지 않습니다.
- 기존 테이블/가격봉/A·B 이벤트 상태/미전송 큐를 초기화하지 않습니다. 신규 bot_watch 테이블과 bot_pending.reply_markup 컬럼은 멱등 생성/추가합니다.
- 신규 계약은 PENDING이며 상태·안내 outbox를 같은 트랜잭션에 기록합니다. 불명확한 과거 계약은 실제 신규 상장으로 단정해 대량 안내하지 않습니다. 상장시각이 확인되면 해당 신규 사건의 안내를 한 번 등록합니다.
- 재상장된 승인 종목은 PENDING 재검토, 차단 종목은 BLOCKED 유지. 같은 재상장의 시각 보완으로 안내나 버튼 버전을 다시 만들지 않습니다.
- 168시간, 90일 완성 4시간봉 최저 종가, 실제 체결가격 3배, A/B 독립성, 신선도, B의 10%·60초 재무장, 기존 이벤트 ID와 전송 재시도는 보존했습니다.
- CoinGecko를 런타임에 호출하지 않습니다. 승인 목록을 자동으로 재선별하지 않습니다.

## 설정과 텔레그램
필수 기존 설정: DATABASE_URL, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID.
선택: HEALTHCHECKS_PING_URL, MAX_PENDING_MESSAGES, TELEGRAM_ADMIN_USER_ID.
개인 채팅의 양수 CHAT_ID는 관리자 from.id로 사용합니다. 그룹/채널은 양수 TELEGRAM_ADMIN_USER_ID를 설정해야 승인·차단을 허용합니다. chat.id와 from.id를 모두 검증합니다.

명령: /status, /status SYMBOL, /status 1, /watch, /pending [페이지], /approve SYMBOL, /block SYMBOL, /review SYMBOL.
신규 안내의 ✅ 승인 / ⛔ 차단 버튼과 명령은 같은 DB 상태를 사용합니다. /review는 REVIEW로 재검토 전환하며 /pending에 함께 표시됩니다.
콜백은 세대 번호 CAS로 멱등 처리하고 DB 실패를 성공으로 표시하지 않습니다. 승인 해제·재승인 시 기존 A/B 전송 상태를 지우지 않습니다.
긴 목록은 페이지로 나눕니다. 발송 성공 시 message_id를 저장하며 원래 안내를 처리 결과로 편집합니다.

## 주기, 장애, 메모리
- EXCHANGE, FUNDING_INFO, LIVE_RECHECK만 각각 180초로 변경했습니다.
- !markPrice@arr@1s, !miniTicker@arr 실시간 수신과 수신 직후 A/B 평가는 유지합니다.
- DIAGNOSTICS는 15초, DB 점검은 5초 등 기존 주기를 유지합니다.
- 별도 2초 점검이 신선도 초과를 감지하면 REST 보완을 시작합니다. 요청 간 최소 10초, 지수 백오프, 공유 403/451 30분·429/418 Retry-After cooldown을 적용합니다. 정기 조회와 장애 복구가 같은 lock을 사용합니다.
- 정상 API에서도 공식 REST에만 나타난 정산 주기 변경은 다음 정기 조회까지 최대 약 180초 늦을 수 있습니다. API 장애/백오프 중에는 더 늦어집니다. 검증된 WS 전환 정보는 즉시 평가하고 신선도 제한은 완화하지 않습니다.
- 원인별 WS 장애 상태를 기존처럼 검사합니다. 통지 방식은 위 v4.1의 자정 일일 보고로 대체하며, 이전 v4의 60초/30분 즉시 통지 억제 상태는 호환성을 위해 보존합니다.
- 진단 억제와 실제 데이터 신선도는 별개입니다. /status에는 실제 장애·미준비 상태가 계속 나타납니다. A/B 메시지에는 진단 억제를 적용하지 않습니다.
- 승인 종목만 SQL에서 가격봉을 선택하고 cursor prefetch=16으로 직접 State를 복원합니다. 미승인 종목의 DB 봉은 읽거나 삭제하지 않습니다. 재승인은 DB 이력을 재사용하고 빈 구간만 보충합니다.
- Candle/State/Event slots, typed-state fingerprints, 2개 이력 worker, 최대 541개 봉·750개 펀딩 이력, 필요한 펀딩 필드만 캐시하여 전체 JSON 복사를 줄입니다.
- Linux 실행 시 분당 RSS·승인 수·봉 수를 stdout에 출력합니다. 실시간 시세/로그 누적 DB를 추가하지 않습니다.
